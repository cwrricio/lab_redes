SSH

Secure Shell: acesso remoto cifrado (porta 22)

Antes dele, o Telnet mandava login, senha e comandos em texto claro. O SSH cifra o canal inteiro desde o primeiro byte.

Teoria · SSH

O que é, quando usar, pontos principais

O que é

Protocolo de rede (RFC 4251) para abrir um shell remoto ou transferir arquivos com toda a comunicação cifrada: senha, comandos, saídas e dados. Roda sobre TCP, normalmente na porta 22.

Quando usar

Administrar servidores remotos, executar comandos num host distante, copiar arquivos com segurança (scp/sftp) e criar túneis cifrados. É o substituto direto de Telnet, rsh e FTP em claro.

Pontos principais

Autenticação por senha ou par de chaves (pública/privada). O servidor prova sua identidade com uma chave de host, defesa contra man-in-the-middle. Um único canal TCP carrega tudo, já cifrado.

Cenário · antes de qualquer comando

Que máquinas eu estou acessando?

Não é um servidor na nuvem nem outro PC da sala. São 3 containers Docker rodando dentro da minha própria máquina, cada um simulando um servidor real:

ssh-server

Servidor SSH (Debian + OpenSSH). IP interno 172.30.0.10.

ftp-server

Servidor FTP (vsftpd). IP interno 172.30.0.20.

ntp-server

Servidor de horário (chrony). IP interno 172.30.0.30.

Os três vivem numa rede Docker isolada chamada labnet (172.30.0.0/24), criada só para o lab. É como uma pequena rede privada dentro do meu computador.

Cenário · como isso subiu

Como as máquinas foram criadas

Tudo está descrito em docker-compose.yml (a "receita" dos 3 servidores) e sobe com um único comando:

# na raiz do projeto, uma vez só, antes da apresentação
make up
  → docker compose build + up   (constrói e liga os 3 containers)
  → gen_keys.sh                 (gera as chaves e configura meu SSH)
# conferir que estão no ar
docker compose ps
lab-ssh   Up   0.0.0.0:2222->22/tcp
lab-ftp   Up   0.0.0.0:21->21/tcp
lab-ntp   Up   0.0.0.0:123->123/udp

Terminal 2: o outro lado

Deixo docker logs -f lab-ssh aberto num canto: a plateia vê o servidor registrando cada conexão em tempo real.

Cenário · a dúvida mais comum

Preciso estar na mesma rede? Não.

Os servidores rodam na minha máquina. Eu os acesso por localhost (127.0.0.1), em portas que o Docker publica do container para o host:

ServiçoPorta no containerPorta no meu PCEu conecto em…
SSH222222localhost:2222
FTP21 (+ dados)21 (+ 21100-21110)localhost:21
SNTP123/udp123/udplocalhost:123
Por que SSH em 2222 e não 22? Porque a minha máquina já pode ter um SSH na 22. Mapear 2222→22 evita colisão. Esse "2222" fica escondido no arquivo de config: eu nunca digito a porta.

Cenário · o primeiro acesso

Como o 1º acesso foi preparado

Ao rodar make up, o script gen_keys.sh deixou tudo pronto dos dois lados, uma vez só:

Na minha máquina (cliente)

1. Gerou meu par de chaves lab_ed25519.
2. Guardou a identidade do servidor em known_hosts.
3. Adicionou 1 linha ao meu ~/.ssh/config criando os apelidos lab e lab-pass.

Dentro do servidor

1. Recebeu minha chave pública em authorized_keys.
2. Ganhou chaves de host fixas (identidade estável).
3. Subiu o sshd ouvindo na porta 22.

Resultado: a partir daí o acesso é um comando curto. De qualquer pasta: ssh lab.
SSH

Os dois lados do SSH, lado a lado

Dentro do servidor: sshd_config

# quem o servidor É (anti-impostor)
HostKey /etc/ssh/ssh_host_ed25519_key
# métodos de login aceitos
PubkeyAuthentication yes
PasswordAuthentication yes
AuthorizedKeysFile .ssh/authorized_keys
PermitRootLogin no

Minha máquina: ~/.ssh/config

# apelido "lab": guarda TODO o resto
Host lab
    HostName 127.0.0.1
    Port 2222
    User labuser
    IdentityFile ~/.../lab_ed25519

Por isso o comando fica só ssh lab: host, porta, usuário e chave já moram no arquivo.

Passo 1Entrar por SENHA

# minha máquina: pede a senha (labpass)
ssh lab-pass

# já dentro do servidor:
hostname   → ssh-server
whoami     → labuser
exit
O apelido lab-pass desliga a chave de propósito, para o servidor pedir a senha: só para demonstrar o método.

No outro lado (docker logs -f lab-ssh)

Accepted password for labuser
   from 172.30.0.1 port XXXXX ssh2

A senha foi pedida, mas não viajou à vista: ela seguiu dentro do canal já cifrado. (No FTP, veremos, ela aparece em claro.)

SSH

Passo 2Entrar por CHAVE (sem senha)

# nenhuma senha é digitada
ssh lab
whoami   → labuser
exit

No log do servidor

Accepted publickey for labuser
   ...ED25519 SHA256:ZUJt...ngn1M

Como funciona sem a senha viajar? Desafio-resposta: o servidor manda um número aleatório, eu assino com a chave privada, ele confere com a pública. O segredo nunca sai da minha máquina.

O SSH é exigente com permissões: 700 na pasta .ssh e 600 no authorized_keys. Se estiver frouxo (ex.: 777), o servidor recusa a chave: assim nenhum outro usuário pode editar quem entra como você.
SSH

Passo 3Transferir arquivo: SCP

# enviar (minha máquina → servidor). Repare: mesmo apelido "lab"
echo "arquivo cifrado de ponta a ponta" > /tmp/oi.txt
scp /tmp/oi.txt lab:              # "lab:" = o lado remoto

# confirmar e baixar de volta
ssh lab 'cat oi.txt'
scp lab:oi.txt /tmp/volta.txt
O scp reaproveita o apelido lab: comando curtíssimo, e tudo roda dentro do SSH, na mesma porta cifrada. Nenhuma porta nova de firewall: diferente do FTP, que veremos precisar de duas.

SSH

A identidade do servidor (anti man-in-the-middle)

Antes de eu provar quem sou, o servidor prova quem ele é, com sua chave de host. Na 1ª conexão o cliente salva a impressão digital em known_hosts:

ssh-keygen -lf client/keys/host/ssh_host_ed25519_key.pub
256 SHA256:/W+H77VCKqG87X9jI...HP9aPM  (ED25519)
Se amanhã um impostor responder com outra chave, o SSH bloqueia com "REMOTE HOST IDENTIFICATION HAS CHANGED". É a defesa contra alguém se passar pelo servidor no meio do caminho.

FTP

File Transfer Protocol: RFC 959 (1985), porta 21

Marca registrada: usa dois canais TCP, um de controle e um de dados. E, no FTP puro, tudo vai em texto claro.

Teoria · FTP

O que é, quando usar, pontos principais

O que é

Um dos protocolos mais antigos da internet (RFC 959, 1985) para transferir arquivos entre cliente e servidor: enviar (STOR), baixar (RETR) e listar (LIST) diretórios remotos.

Quando usar

Hoje, majoritariamente em redes internas controladas ou sistemas legados. Fora desses casos, prefira FTPS ou SFTP, que cifram o que o FTP puro deixa exposto.

Pontos principais

Usa dois canais TCP (controle na porta 21, dados numa porta separada), tem modos ativo e passivo, e autentica com usuário/senha em texto claro por padrão.

FTP

Dois canais e o modo passivo

Canal de CONTROLE (porta 21)

Comandos e respostas: USER, PASS, LIST, RETR (baixar), STOR (enviar), PASV.

Canal de DADOS (porta separada)

O conteúdo do arquivo viaja por outra conexão, numa porta da faixa 21100-21110.

ModoQuem abre o canal de dadosProblema
Ativoo servidor conecta de volta ao clientequebra com NAT/firewall do cliente
Passivo (PASV)o cliente conecta ao servidorfunciona hoje, é o que usamos
Fixamos a faixa 21100-21110 para o Docker conseguir mapeá-la. Sem isso, o servidor sortearia qualquer porta alta e o NAT não saberia encaminhar.
FTP

Ao vivoConectar, enviar e ver o risco

# o -v mostra o diálogo do protocolo: ">" é meu comando, "<" a resposta
curl -v --ftp-pasv -u ftpuser:ftppass ftp://127.0.0.1/
< 220 pronto     > USER ftpuser   < 331 peça senha
> PASS ftppass  < 230 logado    < 227 entrando em passivo

# enviar e baixar um arquivo
curl -T upload.txt ftp://ftpuser:ftppass@127.0.0.1/upload.txt
curl ftp://ftpuser:ftppass@127.0.0.1/exemplo.txt -o baixado.txt
USER ftpuser e PASS ftppass, e o conteúdo dos arquivos, trafegam SEM criptografia. No Wireshark, filtro ftp mostra a senha legível; ftp-data mostra o arquivo. É o método do SSH ao contrário: aqui tudo vaza.
FTP

Isolamento e as versões seguras

Confinamento no servidor

docker compose exec ftp \
  ls -la /home/ftpuser

chroot prende o usuário no próprio home: ele não enxerga o resto do sistema. umask 022 → arquivos 644 (dono escreve, outros só leem).

Substitutos modernos

FTPS

FTP + TLS: cifra os dois canais. Ainda é FTP por baixo (2 canais, porta 21).

SFTP

Não é FTP. É transferência dentro do SSH (porta 22, um canal só). Nomes parecidos, arquiteturas diferentes.

Mantivemos o FTP em claro de propósito: é o que deixa a senha visível no Wireshark e prova por que o FTP puro está obsoleto.

SNTP

Simple Network Time Protocol: RFC 4330, porta 123/UDP

Mantém relógios sincronizados com precisão de milissegundos. Nosso cliente (sntp_client.py) foi escrito do zero, só com a biblioteca padrão.

Teoria · SNTP

O que é, quando usar, pontos principais

O que é

Versão simplificada do NTP (RFC 4330) para sincronizar o relógio de um host consultando um servidor de tempo pela rede, com precisão típica de milissegundos.

Quando usar

Quando um cliente só precisa consultar a hora (não atuar como servidor hierárquico para outros): sistemas embarcados, scripts simples, clientes que não vão operar um daemon completo de NTP.

Pontos principais

Roda sobre UDP na porta 123, organiza servidores em estratos (stratum), usa 4 timestamps por troca para calcular offset e delay, e não autentica o servidor por padrão.

SNTP

Por que UDP, e a hierarquia de stratum

Por que UDP (não TCP)? É uma troca curta pergunta/resposta. O 3-way handshake do TCP adicionaria atraso e distorceria a medição do tempo. Se um pacote se perde, é barato perguntar de novo.

docker compose exec ntp chronyc tracking
docker compose exec ntp chronyc sources -v

Stratum = distância da fonte

0 = relógios de referência (atômico, GPS).
1 = ligados direto a eles.
2, 3… = sincronizam com o nível acima.
Quanto maior o número, mais longe da fonte. Nosso chrony busca o pool.ntp.org e vira stratum N+1.

SNTP

O pacote de 48 bytes e os 4 timestamps

cd client && uv run sntp_client.py --server 127.0.0.1 --raw

Os 4 carimbos de tempo

t1 cliente ENVIOU · t2 servidor RECEBEU
t3 servidor RESPONDEU · t4 cliente RECEBEU

O cálculo

offset = ((t2−t1)+(t3−t4))/2 → quanto meu relógio está adiantado/atrasado
delay = (t4−t1)−(t3−t2) → ida e volta na rede

Assumindo ida ≈ volta, o offset cancela a latência da rede. É por isso que dá para acertar o relógio com precisão de ms mesmo com a rede no meio.
SNTP

Segurança: o NTP básico não autentica

O SNTP/NTP clássico não verifica a identidade do servidor. Um atacante na rede pode responder com hora falsa (NTP spoofing).

Mexer no relógio quebra muita coisa: validade de certificados TLS, logs, Kerberos, tokens TOTP, agendamentos…

Mitigação moderna

NTS (Network Time Security, RFC 8915): autentica o servidor via TLS.

Consulta × sincronização

Nosso cliente consulta e calcula o offset, mas não ajusta o relógio do host: isso é papel de um daemon (chronyd/ntpd) rodando continuamente.

Perguntas prováveis da banca

A senha no SSH vai em claro?

Não, viaja dentro do canal já cifrado. Mas senha é método fraco (segredo compartilhado, sujeito a brute force); chave é melhor.

E se a chave de host mudar?

SSH bloqueia com "IDENTIFICATION HAS CHANGED" e aponta a linha do known_hosts. Você decide se é troca legítima ou MITM.

Por que o FTP usa 2 canais?

Herança de 1985: separa comandos (21) de dados. É o que torna o passivo/NAT complicado, e o SSH resolve tudo numa porta só.

ed25519 vs RSA?

ed25519 usa curva elíptica: chave menor (256 bits ≈ RSA 3072), mais rápida e robusta. Recomendada para sistemas novos.

Por que NTP em UDP?

Troca curta; o handshake do TCP atrasaria e distorceria a medição de tempo. Perda de pacote? Pergunta de novo.

SFTP é o mesmo que FTPS?

Não. SFTP é subsistema do SSH (porta 22, 1 canal). FTPS é FTP antigo embrulhado em TLS (porta 21, 2 canais).

Conclusão

Mesma pergunta, três respostas.

SSH

Acesso remoto com o canal inteiro cifrado. Chave > senha.

FTP

Simples e antigo, e por isso, em claro. Hoje: FTPS ou SFTP.

SNTP

Tempo preciso via 4 timestamps. Sem autenticação → NTS.
