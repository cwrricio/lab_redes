SSH

Secure Shell

RFC 4251 . 4252 . 4253 . 4254 | Protocolo SSH-2

Contexto

O problema antes do SSH

Telnet e rlogin (antes de 1995)

Login, senha e comandos viajavam em TEXTO CLARO. Qualquer pessoa na rede capturava tudo com um sniffer.

SSH (1995, Tatu Ylonen)

Criado na Finlandia apos um ataque de sniffing. Cifra o canal inteiro desde o primeiro byte.

Em 1995 a senha de Tatu Ylonen foi capturada por um sniffer na rede universitaria. Ele criou o SSH em resposta.

SSH-1 (1995) tinha vulnerabilidades. SSH-2 (2006, RFCs 4251-4254) e a versao atual.

Para que serve

Usos do SSH

Shell remoto

Acesso ao terminal de qualquer servidor, de qualquer lugar.

SCP e SFTP

Transferencia de arquivos cifrada sobre o mesmo canal.

Tuneis

Redirecionar portas locais para o servidor. VPN basica pelo SSH.

Automacao CI/CD

Deploy, scripts de infra, autenticado por chave sem senha.

Git (GitHub/GitLab)

git clone git@github.com usa SSH por baixo.

Administracao

Linux, roteadores, switches, dispositivos embarcados.

Protocolo

Arquitetura em 3 camadas

3. SSH Connection (RFC 4254)

Multiplexa canais logicos: sessao interativa, SCP, port forwarding. Tudo na porta 22.

2. SSH User Authentication (RFC 4252)

Dentro do canal cifrado, o cliente prova quem e: por senha, por chave publica.

1. SSH Transport Layer (RFC 4253)

Base: abre o TCP, negocia algoritmos, cifra o canal. O servidor tambem se autentica aqui pela chave de host.

Rede

Porta 22 e acesso pelo mundo

Porta 22 e a porta well-known do SSH (IANA). Qualquer porta poderia ser usada; 22 e a padrao.

Na mesma rede local: ssh labuser@192.168.1.100 - funciona se voce estiver conectado ao mesmo roteador ou VPN.
Pela internet, de qualquer lugar do mundo: ssh labuser@203.0.113.10 - basta o servidor ter um IP publico e a porta 22 acessivel. O protocolo e identico.

Atras de NAT: use port forwarding no roteador, uma VPN, ou servicos como Tailscale.

# mesma rede local
ssh labuser@192.168.1.100

# internet (IP publico)
ssh labuser@203.0.113.10

# com porta diferente
ssh -p 2222 labuser@servidor.com

# nosso lab (container Docker)
# 127.0.0.1:2222 -> 172.30.0.10:22
ssh -p 2222 labuser@127.0.0.1

Configuracao

O arquivo ~/.ssh/config

Sem um arquivo de configuracao, cada conexao exige digitar todos os parametros.

# comando sem config:
ssh -p 2222 -i ~/.ssh/id_ed25519 \
  -o IdentitiesOnly=yes \
  labuser@127.0.0.1

Com o arquivo ~/.ssh/config, voce define aliases:

ssh lab
ssh maquina1
O ssh_config do laboratorio ja esta configurado em client/ssh_config com o alias lab. 
# ~/.ssh/config

Host lab
    HostName 127.0.0.1
    Port 2222
    User labuser
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes

Host maquina1
    HostName 192.168.1.100
    Port 22
    User ubuntu

Host producao
    HostName 203.0.113.10
    Port 22
    User deploy
    IdentityFile ~/.ssh/id_deploy

Identidade do Servidor

Chave de host: protecao contra MITM

Antes de voce se autenticar, o servidor prova quem e. Ele tem um par de chaves de host. O cliente salva a fingerprint em ~/.ssh/known_hosts.

Se um impostor se passar pelo servidor com outra chave...

REMOTE HOST IDENTIFICATION HAS CHANGED! O SSH bloqueia e alerta sobre possivel MITM.
Aceitar yes na pergunta inicial sem verificar a fingerprint e um habito perigoso. 
# Fingerprint da chave de host
ssh-keygen -lf ssh_host_ed25519_key.pub
256 SHA256:DsXYiKI5AeTjmf... (ED25519)

# known_hosts do cliente (mesma fingerprint)
cat client/keys/known_hosts
[127.0.0.1]:2222 ssh-ed25519 AAAAC3Nz...

# Na primeira conexao:
The authenticity of host '[127.0.0.1]:2222'
can't be established.
ED25519 fingerprint is SHA256:DsXY...
Are you sure you want to continue (yes/no)?

Criptografia

O canal cifrado

Confidencialidade

Conteudo inelegivel para quem capturar os pacotes. Comandos, arquivos, senhas: nada pode ser lido.

Autenticidade

Voce sabe com quem esta falando. A chave de host garante que nao e um impostor.

Integridade

Impossivel alterar um byte sem ser detectado. O SSH autentica cada pacote.

Como: antes de qualquer dado sensivel, cliente e servidor fazem uma troca matematica de chaves (Diffie-Hellman) e chegam ao mesmo segredo sem nunca transmiti-lo pela rede. 
# /etc/ssh/sshd_config (nosso lab)

# Troca de chaves
KexAlgorithms curve25519-sha256

# Cifra do canal
Ciphers chacha20-poly1305@openssh.com

# Verificacao de integridade
MACs hmac-sha2-512-etm@openssh.com

Autenticacao

Metodo 1: Usuario e Senha

O metodo mais simples. O cliente envia usuario e senha dentro do canal ja cifrado.

A senha NAO vai em texto claro. Ela viaja dentro do canal cifrado (diferente do Telnet e do FTP).
Vulneravel a brute force: bots varrem a porta 22 da internet testando milhares de senhas por hora. Se a senha for fraca, e questao de tempo.
Tambem vulneravel a phishing, reuso de senha e vazamentos de banco de dados. 
# Login por senha
# (vai pedir: labpass)
ssh -p 2222 labuser@127.0.0.1

labuser@127.0.0.1's password: ****

# Dentro do servidor
labuser@ssh-server:~$ hostname
ssh-server
labuser@ssh-server:~$ whoami
labuser

# Log do servidor confirma:
Accepted password for labuser

Autenticacao

O par de chaves assimetricas

Chave Privada

Fica so na sua maquina. Nunca sai daqui. Idealmente protegida por passphrase. Path: ~/.ssh/id_ed25519

Chave Publica

Vai para o servidor, em ~/.ssh/authorized_keys. Pode ser distribuida a vontade. Sozinha nao serve para nada.

Como funciona o login: servidor gera um desafio. Cliente assina com a privada. Servidor verifica com a publica. Nenhum segredo viaja pela rede. Imune a brute force. 
# Gerar um par ed25519
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519

# Ver a chave publica
cat ~/.ssh/id_ed25519.pub
ssh-ed25519 AAAAC3NzaC1lZD... labuser@maq

# Instalar no servidor
ssh-copy-id -i ~/.ssh/id_ed25519.pub user@servidor

# O que vai para authorized_keys:
ssh-ed25519 AAAAC3NzaC1lZD... labuser@maq

Ed25519 usa curva eliptica. Mais seguro e rapido que RSA para o mesmo nivel de protecao.

Autenticacao

Metodo 2: Chave Publica

Com a chave publica instalada no servidor, o login acontece sem digitar senha.

Imune a brute force: nao ha senha para adivinhar. Nenhum segredo trafega.
Permite automacao: scripts, CI/CD, deploy sem senha hard-coded.
Um par de chaves, varios servidores: a mesma chave publica instalada em dezenas de maquinas. 
# Login por chave (sem senha)
ssh -F client/ssh_config lab

Welcome to Debian GNU/Linux 12
labuser@ssh-server:~$

# Log do servidor:
Accepted publickey for labuser
ED25519 SHA256:jejldHgbSLC...

# Verificar a fingerprint aceita:
ssh-keygen -lf client/keys/lab_ed25519.pub
256 SHA256:jejldHgbSLC... (ED25519)

Seguranca em Disco

Permissoes: o SSH recusa chaves erradas

O sshd rejeita autenticacao por chave se as permissoes estiverem incorretas. Motivo: outro usuario do sistema poderia editar o authorized_keys e entrar como voce.

Caminho Permissao Significa
~/.ssh/ 700 so o dono entra no diretorio
authorized_keys 600 so o dono le e escreve
chave privada 600 so o dono le e escreve
Experimento ao vivo: chmod 777 ~/.ssh/authorized_keys e o SSH recusa a chave. 
# Verificar permissoes no servidor
stat -c "%a  %n" ~/.ssh ~/.ssh/authorized_keys
700  /home/labuser/.ssh
600  /home/labuser/.ssh/authorized_keys

# Com permissao incorreta (777):
chmod 777 ~/.ssh/authorized_keys
ssh labuser@servidor
Authentication failed.
# sshd rejeita silenciosamente

# Corrigir:
chmod 600 ~/.ssh/authorized_keys

Transferencia de Arquivos

SCP e SFTP: arquivos sobre o SSH

SCP e SFTP rodam dentro do SSH: mesma porta 22, mesma criptografia. Sem abrir nova porta no firewall.

SCP

Copia simples, estilo cp. Um comando, arquivo copiado.

SFTP

Sessao interativa com put, get, ls, rm. Interface tipo FTP mas completamente cifrada.

SFTP nao e FTPS. SFTP e um subsistema do SSH (porta 22, 1 canal). FTPS e FTP com TLS (porta 21 + canal de dados). Nomes parecidos, arquiteturas diferentes. 
# Enviar arquivo: LOCAL para REMOTO
scp -P 2222 -i client/keys/lab_ed25519 \
  /tmp/relatorio.txt \
  labuser@127.0.0.1:/home/labuser/

# Baixar arquivo: REMOTO para LOCAL
scp -P 2222 -i client/keys/lab_ed25519 \
  labuser@127.0.0.1:/home/labuser/arquivo.txt \
  /tmp/

# SFTP interativo
sftp -F client/ssh_config lab
sftp> ls
sftp> put /tmp/relatorio.txt
sftp> get relatorio.txt /tmp/
sftp> bye

Boas Praticas

Hardening SSH em producao

# /etc/ssh/sshd_config (producao)

# Nunca root diretamente
PermitRootLogin no

# So chave publica, sem senha
PasswordAuthentication no

# Bloqueia brute force rapidamente
MaxAuthTries 3
LoginGraceTime 20

# Whitelist de usuarios
AllowUsers deploy jenkins

# Algoritmos modernos
KexAlgorithms curve25519-sha256
Ciphers chacha20-poly1305@openssh.com
MACs hmac-sha2-512-etm@openssh.com

fail2ban

Bane automaticamente IPs apos N tentativas falhas. Essencial para porta 22 publica.

Firewall

Libera porta 22 so de IPs especificos. ufw allow from IP to any port 22

Passphrase na chave privada

Se a chave for roubada, ainda esta protegida. Use: ssh-keygen -p

Limitacoes do Experimento

O que ficou de fora

  • Tudo em loopback (127.0.0.1): em um cenario real, cliente e servidor estao em maquinas diferentes em redes distintas.
  • PasswordAuthentication yes: mantivemos para demonstrar os dois metodos. Em producao: so chave mais PasswordAuthentication no.
  • Passphrase na chave privada: a chave do lab nao tem passphrase para facilitar a demonstracao. Em producao, proteja a chave privada.
  • Sem fail2ban e firewall: itens de producao fora do escopo do lab.
  • Sem port forwarding nem VPN: o acesso pela internet exige configuracao de rede no roteador ou servico de tunelamento.

Conclusao

SSH resolve o acesso remoto seguro.

Canal cifrado

Ninguem na rede le seus comandos ou arquivos.

Chave publica

Sem segredo viajando pela rede. Imune a brute force.

Tudo na porta 22

Shell, SCP, SFTP, tuneis. Um unico canal cifrado.
